#Code Review team-bottleneck

###Позитивні аспекти

- Функції та серіалізатори компактні, кожна виконує одну чітку дію — код легко читати та підтримувати.
- Логіка проєкту чітко розділена на частини - компоненти, серіалізатори, моделі і т.д.
- Використовуються корисні практики: async/await, DRF, ModelSerializer, JWT, базова валідація полів.
- API URL формуються логічно, іменування функцій уніфіковане (getX, makeX, removeX).

###Проблеми та недоліки

- Непостійна обробка API: десь є normalize (response.data.results), десь ні; деякі функції не повертають результат (наприклад deleteParkingLot).
- Часте дублювання логіки, наприклад: порівняння lot_id у permissions, перевірка coordinates у серіалізаторах, обробка response.data.
- Локальна консистентність слабка: поєднуються прямий axios і apiClient без єдиного підходу.
- Відсутня централізована обробка помилок, а тому сирі помилки кидатимуться у UI, що може призвести до некоректного стану інтерфейсу.
- Незрозумілі debug-повідомлення (print(f"DEBUG…")) та обмежена документація (docstrings/JSDoc) знижують підтримуваність.
- Перевірка даних недостатня: будь-які credentials, userData, bookingData відправляються як є, потенційно відкриваючи шлях до ін’єкцій.

###Потенційні ризики

- JWT токени зберігаються у localStorage, а це потенційний ризик XSS-атаки.
- Генерація OpenAPI у AppConfig.ready() може викликати race condition у production.
- Валідація даних у серіалізаторах частково ручна, що збільшує ризик логічних помилок або некоректних даних.
- Відсутність обробки помилок у API-функціях (deleteParkingLot, інші), через що UI може вважати операцію успішною, хоча сервер повернув помилку, що призводить до втрати синхронізації стану.

###Пропозиції поліпшення

- Уніфікувати обробку API-відповідей: винести логіку response.data.results ?? response.data у окрему утиліту.
- Додати обробку помилок (try/catch) у всі API-функції, щоб уникнути збоїв і мати змогу показувати помилки у UI.
- Зберігати токени (JWT) через cookies, щоб унеможливити XSS-атаки.
- Додати мінімальні JSDoc-коментарі або типи для вхідних даних (lotData, userData тощо) для підвищення підтримуваності та зрозумілості коду.
