# Есе-рефлексія: командна робота та етичні виклики

**Команда:** team-badhabits  
**Студент:** Козін Андрій

## Роль та організаційні виклики

Протягом проєкту я виконував ролі Issue Tracker Lead, Quality Lead та Traceability Lead у команді. Моя робота - організація робочого процесу: створення GitHub issues, code reviews, та інтеграція CI/CD.

Найбільшим викликом виявилося розподілення задач у команді з урахуванням технічних преференцій кожного. Виявилось, що у всіх є свої мови програмування, які вони знають, і писати на чомусь новому особливо немає бажання. Це створювало складнощі при плануванні, треба було балансувати між ефективністю розробки та навчанням нових технологій. Зрештою ми знайшли компроміс(не найкращий як на мене, але що маємо): Flutter frontend розподілили між тими, хто готовий був його вчити, а backend взяли ті, хто вже мав досвід з Node.js.

## Комунікація та синхронізація

Найважливіше що я зрозумів - треба регулярно сінкатися. Спочатку ми працювали досить автономно та просто пушили код і бачили зміни один одного на GitHub. Але з часом зрозумів, що набагато легше, коли хтось пояснює свою частину коду і що він робить, а не просто дивишся на diff у PR. Це особливо допомогло при інтеграції складних частин, як-от адаптивна система тренувань з Firestore queries.

## Технічні уроки

Найбільшим технічним сюрпризом було те, наскільки складний iOS для deployment та навіть просто локального запуску. Щоб просто запустити Flutter app на iOS емуляторі, потрібен Xcode, налаштування signing certificates, provisioning profiles - це прям дофіга гемору порівняно з Android, де достатньо встановити емулятор і все працює. Зрозумів, що кросплатформенна розробка насправді не така "write once, run everywhere", як здається.

## Що б зробив інакше

Якби почав заново, я б не робив проєкт з голою Firebase без нормального backend. Хоча Firebase зручний для MVP, відсутність proper API ускладнила багато речей, наприклад, складні queries та бізнес-логіка виглядають краще на backend, ніж розкидані по client-side коду. 

Також я б одразу впроваджував тести замість додавання їх наприкінці. TDD підхід заощадив би час на debugging та рефакторинг.

## Висновок

Цей проєкт показав, що командна робота - це не лише про розподіл технічних задач, але й про розуміння сильних сторін кожного члена команди, регулярну комунікацію та готовність адаптуватись до обставин. Найважливіший урок - планування архітектури та тестів на початку окупається десятикратно протягом розробки.
